# 호영의 원문 검토 계약

호영은 받은 원문과 검토 결과를 구분한다. 대화 원본은 요약이나 검색 캐시와 별도로 보존하고, 사용자 발화의 검토 진행은 SQLite에 저장한다. 이 문서에서 ‘검토됨’은 모델이 특정 원문의 정확한 범위를 읽었다고 구조적으로 확인한 상태다. 모든 의미를 정확하게 이해했거나 모든 개인 사실을 기억으로 추출했다는 증명은 아니다.

## 정확히 어떤 범위를 검토했는가

`MemoryReviewCoordinator.prepareBatch()`는 사용자 발화만 대상으로 한 번에 최대 16개 원문, 24,000 UTF-16 문자, 원문 하나당 최대 8,000 문자를 제공한다. 큰 원문은 다음 오프셋부터 계속한다. 대리 쌍을 쪼개지 않는다. 각 범위에는 메시지 ID, 시작과 끝 오프셋, 원문 SHA-256, 레코드 해시가 포함된다. `prepareBatch(int maxSerializedChars)`는 JSON 이스케이프와 맥락을 포함한 실제 직렬화 길이를 제한한다. 기본 한도는 60,000문자다. 한도를 넘으면 맥락을 줄이고 뒤 원문들을 다음 배치로 미루거나 첫 청크를 더 작게 읽는다. 제외된 범위는 진행된 것으로 표시하지 않는다. 맥락의 텍스트가 생략되면 출처 ID와 오프셋을 통해 더 읽어야 한다. 배치 ID는 정확한 검토 범위와 커서에서 계산하며, 대화 맥락이 추가돼도 같은 범위의 ID는 유지된다.

짧은 확인 표현을 해석하도록 앞의 두 메시지와 뒤의 한 메시지에서 제한된 맥락을 제공한다. 원문이 잘리는 지점에는 앞뒤 최대 512문자의 겹침을 제공한다. `contextMessages`, `contextBefore`, `contextAfter`는 모두 `context_only_not_acknowledged`다. 이 맥락은 의미를 이어주는 자료이며, 해당 메시지나 겹침 영역 전체를 이미 검토했다고 주장할 수 없다. 조수 발화는 사용자 사실의 직접 증거로 바뀌지 않는다. 맥락도 제한되어 있으므로 필요한 경우 원문 읽기 도구로 더 확인해야 한다.

## 진행을 확정하는 조건

`acknowledge()`는 배치 ID, 모든 원문 범위와 해시, 명시적인 `noMemoryNeeded` 결정, 제안한 기억의 실제 저장 결과를 확인한다. 저장 실패, 누락된 범위, 불일치한 결정, 오래된 배치, 읽을 수 없는 원문, 변경된 원문은 커서를 진행시키지 않는다. 원문 재확인과 커서 비교·진행은 같은 저장소 트랜잭션에서 처리한다. 사라진 파일을 건너뛰지 않으며, 확인할 수 있는 앞부분만 진행하고 막힌 뒷부분은 보류할 수 있다.

건강, 알레르기, 정정, 지속적 선호, ‘기억해’ 등 일부 중요 표현을 휴리스틱으로 감지한다. 이러한 범위에 `noMemoryNeeded:true`를 반환하면 첫 응답만으로 진행하지 않고 `second_pass_required`를 기록한다. 다음 배치는 `secondPassRequired:true`와 이전 이유를 제공한다. 다시 검토한 응답은 `review.secondPass:{reviewed:true,reason:"..."}`를 포함해야 한다. 이는 실수로 중요 정보를 버릴 가능성을 낮추는 추가 확인이다. 표현 탐지는 한국어·영어의 제한된 패턴이며, 누락과 오탐이 있다. 두 번째 모델 확인도 실제 의미 추출의 완전성을 입증하지 않는다. 이미 기억이 존재한다는 이유로 새 원문의 출처나 정정을 무시하지 않도록 프롬프트와 실제 저장 근거를 함께 검토해야 한다.

## 재검토

`requestRevisit(fromMessageIdInclusive,throughMessageId,reason)`은 별도 커서와 고유 세대 ID를 가진 재검토를 시작한다. 기존 누적 검토 워터마크는 뒤로 가지 않는다. 진행 중인 재검토를 다른 요청으로 덮어쓰지 않는다. `hasPending()`과 `status()`는 새 원문 및 재검토 진행을 모두 반영한다. 오래된 사실의 정정 관계, 추출 정책 변경, 사용자의 기억 누락 신고에 이 API를 사용할 수 있다. 주기적인 전체 재검토를 자동으로 수행한다고 주장하지 않는다.

## 현재 적용 범위와 검증 한계

텍스트 커서는 사용자 메시지의 저장된 텍스트에 적용된다. 첨부 원본은 아래의 별도 분석 상태로 추적한다. 첨부 이미지의 모든 시각 정보, 오디오 전사, 외부 서비스의 숨겨진 기록, 전달되지 않은 내용까지 검토했다고 주장하지 않는다. 휴대폰 관찰은 별도 이벤트 원본과 출처를 사용한다. 모든 검토가 끝나도 특정 기억이 필요한 순간에 검색되는지는 별도의 검색·시간 관계·의미 추출 평가가 필요하다. 1~2년 원문 보존 설계와 인공 장기 기록 테스트는 실제 1~2년 사용 결과 또는 완벽한 기억의 증명이 아니다.

테스트는 범위 누락, 저장 실패, 오래된 응답, 마지막 청크, UTF-16 원문 재구성, 읽기 실패, 해시만 유지한 내용 변경, 짧은 확인의 맥락, 경계의 부정 표현, 중요 원문의 추가 확인, 재검토의 커서 독립성을 확인한다. 실제 모델이 어떤 사실을 놓치는지는 이러한 구조 테스트와 따로 측정해야 한다.


## 첨부 원본과 분석 상태

첨부 원본의 SHA-256과 사용자 메시지를 연결하는 `assetCoverage:<messageId>` 기록을 사용한다. 텍스트를 검토하거나 ‘기억할 내용 없음’으로 확인해도 이미지를 읽은 것으로 처리하지 않는다. 원문을 모두 검토한 뒤에도 분석하지 않은 첨부가 있으면 `reviewMode:asset` 배치를 제공한다. 해당 배치의 텍스트는 캡션 문맥일 뿐이며, 기존 텍스트 커서는 움직이지 않는다.

`raw_saved` 또는 `needs_reanalysis` 첨부는 미완료 상태다. 실제 첨부가 연결된 Work 요청과 그 요청에 대응하는 제공자 분석 응답을 런타임이 관찰한 경우에만 `acceptAssetAnalysis()`로 `provider_analyzed` 상태를 기록한다. 신뢰할 수 있는 영수증에는 사용자 원문 ID, 첨부 ID·SHA, 제공자 요청 ID, 업로드 관찰, 응답 관찰, 분석 텍스트 SHA, 저장된 원 응답 SHA가 필요하다. 현재 요청의 첨부 메타데이터와 저장된 응답 해시도 일치해야 한다. 모델의 일반 기억 검토 확인이나 로컬 첨부 메타데이터만으로 이 상태를 만들 수 없다.

제공자 분석 텍스트는 조수 원문으로 그대로 저장한다. 검색을 위한 파생 기억은 `observation`, `provenance:provider_asset_analysis`, `analysisVerified:false`로 저장하고 원본 첨부 SHA와 분석 원문 ID를 남긴다. 큰 분석은 파생 기억에서 짧게 보여도 전체 원문이 별도로 남는다. 제공자가 그 이미지를 분석했다는 보고와 이미지의 모든 사실을 정확히 파악했다는 주장은 다르다. `provider_analyzed`도 독립적 의미 검증이나 완벽한 이미지 이해의 증명이 아니다.

실제 분석 원문보다 나중의 사용자 발화를 연결하면 `user_confirmed` 상태를 별도로 기록할 수 있다. 확인 발화가 존재한다는 것은 확인의 의미 범위까지 자동 검증한 것이 아니므로 `analysisVerified`는 계속 `false`다. 사용자의 직접 사실·선호는 해당 발화 원문의 정확한 인용을 검증하는 일반 기억 저장 절차를 거쳐야 한다. 재분석을 요청하면 이전 원문과 기억을 지우지 않고 해당 첨부를 다시 미완료 상태로 남긴다.

미완료 첨부만 `pendingAssetReview:<19자리 메시지 ID>` 인덱스에 둔다. 상태 갱신과 미완료 개수는 같은 트랜잭션에서 반영한다. `assetsPending`은 첨부 개수이고 `assetSourcesPending`은 해당 사용자 메시지 개수다. 오래된 메시지는 제한된 묶음으로 발견하며, 새 메시지는 `registerAssetSource()`로 즉시 등록한다. 발견 커서, 분석 커서, 텍스트 커서를 따로 보여준다. 분석 커서는 발견된 범위에서 앞선 미완료 첨부가 없는 지점을 뜻하며, 재분석 요청 시 다시 낮아질 수 있다. 과거 데이터의 파일 ID만 있고 원본 SHA가 확인되지 않으면 분석 근거를 검증했다고 표시하지 않는다.

단위 테스트는 실제 사설 파일에 보존된 첨부와 합성 제공자 영수증으로 상태 계약을 확인한다. 실제 ChatGPT Work 업로드·이미지 분석·계정 연결을 성공했다고 증명하는 테스트가 아니다. 웹 브리지의 업로드 관찰 의미와 실제 계정에서의 동작은 별도로 검증해야 한다.


## 분석 상태 손상과 확인 응답

분석 상태의 JSON·첨부 개수·원본 SHA·제공자 분석 출처·관찰 영수증이 손상되면 분석이 끝났다고 간주하지 않는다. 원래 메시지의 불변 첨부 메타데이터로 `raw_saved` 상태를 재구성하고, 손상된 이전 기록을 별도 내부 원문과 해시로 남긴다. 원본 메타데이터도 읽을 수 없으면 `pendingUnknownAssets`로 미확인 상태를 유지한다. 이전 분석 원문이나 파생 기억은 삭제하지 않는다.

미완료 상태는 읽을 때 다시 확인하고, 완료된 옛 상태도 사용자 원문 32개씩 순환하는 로컬 무결성 점검으로 확인한다. 이 점검 자체는 제공자를 호출하지 않는다. 큰 기록의 전체 점검은 여러 번에 나뉘므로 모든 과거 손상을 즉시 발견한다고 주장하지 않는다. `assetIntegrityAuditCursor`는 이 점검의 진행이며 텍스트 검토 커서와 다르다. `originalIdentityMetadataVerified`는 파일 ID·SHA가 보존된 메타데이터에서 일치한다는 뜻이며 현재 파일 바이트를 새로 검증한 것과 구분한다. 실제 업로드 경로는 다시 원본 바이트를 검증한다.

첨부 전용 배치의 일반 확인 응답은 첨부 상태를 바꾸지 않는다. 해당 배치의 모든 첨부 ID·SHA가 현재 원본과 정확히 일치하고, 이미 저장된 실제 제공자 분석 원문·관찰 영수증이 검증될 때만 `asset_receipts_verified`를 기록할 수 있다. 일부 첨부가 미완료이거나 출처·영수증이 읽히지 않으면 실패한다. 성공해도 텍스트 워터마크와 첨부 단계는 움직이지 않으며, 이미지 의미를 독립적으로 검증했다고 표시하지 않는다.


동일한 원본 바이트가 다른 첨부 ID·파일 형식으로 들어온 경우에도 각 첨부의 분석과 영수증을 따로 보존한다. 제공자 분석 키와 영수증 키는 사용자 메시지 ID·원본 SHA·첨부 ID 해시를 함께 사용한다. SHA만 같다는 이유로 다른 첨부의 분석 증거를 덮어쓰지 않는다. 이전 형식의 영수증은 실제 첨부 ID가 일치할 때만 호환 경로로 읽는다.
