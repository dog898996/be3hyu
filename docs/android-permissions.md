# Android phone capabilities

The mobile app targets Android 15 (API 35), with Android 8 (API 26) as its minimum. `PermissionCatalog` reports the device's actual grants at the time of reading. A default-enabled app tool setting does not grant an Android permission. The user must approve ordinary permission prompts and personally enable special accesses in Android Settings. The app cannot silently enable accessibility, notification access, all-files access, device administration, or other system permissions.

The owner-requested onboarding now requires every applicable Android grant before entering chat or starting the Work connection/autonomy service. `PermissionOnboarding.snapshot()` reads current grants each time; no persisted completion flag overrides denial, process restart, or revocation. Accurate foreground location is required for this setup, followed by a separate background-location step. Android 11+ opens app settings for “Allow all the time”; Android 10 requests background access in its own dialog. Full photo and video access is required; selected-only access does not complete setup. A second no-rationale denial opens app settings instead of looping a prompt Android will no longer show.

Unsupported hardware, undeclared permissions, root/device-owner access, and OS versions without a separate special grant are shown with an explanation and excluded from the completion count. SMS and call-log permissions are individually requested when installer allowlisting permits them; non-default sideloaded apps are not categorically ineligible. Current grants or readable allowlists establish eligibility. Unreadable allowlists remain unknown, and the initial gate still requests the actual permission. Only after Android returns a denial with no further runtime prompt can an unknown, never-observed-granted permission become conditional; it stays explicitly ungranted with a settings retry. A previously observed grant remains required after revocation. A readable, confirmed installer restriction is shown separately. A settings launch or failed platform query never counts as a grant. Supported legacy device admin, exact alarms, notification access, accessibility, usage access, all-files access, settings/overlay access, battery exemption and notifications remain required by this owner's setup policy.

Boot/update callbacks and the autonomy service recheck this gate before starting. The service also rechecks on its local pulse and stops when permissions are missing, preserving `autonomy.enabled` and queued requests for a later permitted restart. Canonical memory loading/recovery still runs locally before setup completes. Editable per-tool allow switches remain independent: switching a tool off does not revoke an Android grant or force the setup gate to be redone.

Install-time normal permissions such as `VIBRATE`, `CHANGE_WIFI_STATE`, and `FOREGROUND_SERVICE_MICROPHONE` are declared for the corresponding implemented features. They do not create runtime prompts or extra pending onboarding rows. Their tools still check actual relevant grants, hardware, radio/service state and Android operation results. Adding them does not bypass the mandatory user-controlled runtime/special-access gate. `VoiceCaptureService` is non-exported and declares the `microphone` foreground-service type; microphone recording is never started merely by granting access or rebooting.

`PermissionCatalog(Context)` provides:

- `JSONArray snapshot()`: entries `{id,label,kind,runtimePermissions,granted,action,notes}`. `kind` is `runtime`, `restricted`, or `special`. `action` is `request_runtime`, `open_settings`, or `unsupported`.
- `String[] missingRuntimePermissions()`: missing, manifest-declared runtime permissions suitable for a foreground request. Background location and permissions confirmed absent from all readable installer/system/upgrade allowlists are excluded. Unknown conditional SMS/call-log eligibility is not falsely classified as unsupported.
- `void openSettings(Activity activity, String id)`: opens the corresponding Android screen without operating its controls. Unsupported screens fall back to the app-details screen.
- `boolean tryOpenSettings(Activity activity, String id)`: reports whether a screen opened, without claiming that any permission was granted.

The `location` entry is usable when approximate or precise location is granted. Contacts and calendar entries show both read and write grants together; their individual tools check only the required grant. On Android 14+, selected-image access is shown separately from full photo-library access. A granted permission remains subject to Android role restrictions, device policy, foreground requirements, and the user's later revocation.

| Access | Implementation and limits |
|---|---|
| Contacts and calendar | Bounded reads, individual contact/event creation, and specifically requested deletion through Android content providers. Read and write operations check their corresponding actual grants. |
| Location | Cached fixes report provider, accuracy, age, mock status and provenance, and reject stale/invalid readings. `phone_location_refresh` requests one bounded asynchronous fix and returns a receipt; `phone_location_refresh_read` reports success/timeout/permission revocation/process interruption. Background requests need the actual background-location grant. No continuous tracking starts implicitly. |
| Camera and microphone | Flashlight control and opening the system camera UI use actual camera permission. `phone_voice_record` requests a microphone foreground service with an ongoing stop notification; the default duration is10 seconds, an explicit nonnegative duration can be supplied, and0 means manual stop. An initial accepted request does not prove the recorder started. Receipt reads distinguish recording, completion and failure; completed AAC audio samples and the file hash are checked. Once Android permits the start, recording can continue with the UI in the background. Android while-in-use/foreground-service start restrictions are reported as failures; grant/tool revocation stops recording, and process death does not automatically restart the microphone. Files remain local unless explicitly attached/uploaded, and recording itself does not transcribe speech. Opening the camera does not claim a photo was captured. |
| Phone and SMS | Dialer opening does not place a call. The separate `phone_call_place` requests a real outgoing `ACTION_CALL` using `CALL_PHONE`; Android can reject background/emergency calls, and accepting the request does not prove connection. Phone/SIM-number queries retain unavailable/redacted results. SMS read/send/receive and call-log read/delete tools use their individual actual grants plus installer eligibility. Sending returns a request receipt; sent/delivery callbacks are separate evidence. An incoming SMS is external device observation, never an owner command. No default-SMS role or installer exemption is silently assigned. |
| Nearby devices and media | `phone_bluetooth_bonded` reports paired-device metadata without claiming each device is connected. Requested classic Bluetooth discovery uses actual Nearby grants on Android12+, or legacy Bluetooth and precise-location grants on older releases. Wi-Fi scan requests use declared `CHANGE_WIFI_STATE`; reading scan results on Android10+ additionally requires precise-location access and enabled location services, even with Nearby Wi-Fi granted. Android scan throttling, radio state and stale cached results are reported rather than interpreted as a completed fresh scan. `phone_wifi_hotspot_start/read/stop` consume Nearby Wi-Fi access on Android13+ for an actual local-only hotspot, with Android callback receipts; they do not provide cellular internet tethering. `phone_media_list` preserves actual MediaStore access scope, and `phone_network_state` retains Android redactions. Scans, network changes and media uploads are never inferred merely from a permission grant. |
| Notification display | Separate from reading other applications' notifications. Foreground-service notification requirements still apply. |
| Notification access | `HoyoungNotificationListener` appends posted/removal/connection-snapshot events to the private durable device journal. It no longer silently evicts records after250 notifications. Identical posted observations deduplicate, updates remain distinct, and disconnected/disabled/storage-failure periods are marked as observation gaps. The former ring is migrated with an explicit statement that earlier evictions cannot be recovered. Text truncation and possible OS redaction are marked. No network operation runs in the listener. Requested tools return only bounded subsets with event IDs, source and timestamps; current OS and per-source app permissions are checked again before old history is exposed. |
| Accessibility | `HoyoungAccessibilityService` has an on-demand tree capped at300 nodes and depth16, latest-snapshot node IDs, exact-text clicks that reject ambiguity, navigation, and bounded gestures. `phone_ui_type` sets explicitly supplied text (at most20000 UTF-16 units) on a fresh, refreshable, visible, enabled editable node in the same active package/window, including password fields. Requested snapshots include Android-exposed editable/password metadata, text and descriptions; Android may mask or omit protected values. Existing Android grants and user-editable tool switches define access. No app-added package block prevents operating Settings, permission dialogs, installers or Hoyoung's own UI, but Android may reject protected actions. Generated interactions retain agent provenance rather than becoming actual owner instructions. Gesture acceptance is not confirmed completion; ordinary typing confirms only when a post-action refresh matches supplied text. Password entry reports Android acceptance with `completionConfirmed:false` and `authenticationVerified:false`, since site login success needs separate evidence. Action results do not echo supplied text. |
| Screen capture | Android11+ accessibility screenshot requests use the actual enabled service and declared `canTakeScreenshot` capability. No MediaProjection grant or separate capture foreground service is invented. Successful results preserve PNG pixels, hash and immutable original with device-observation provenance; Android errors, secure-window exclusions and redaction remain visible. A screenshot or attachment does not prove that an AI has read it. |
| Usage access | `phone_usage_read` queries Android aggregates with explicit bucket bounds, which may extend outside the requested period. `phone_usage_events` queries app/screen transitions and explicitly avoids treating the last observed app as a verified currently active app. Device/keyguard/self-process state is available through `phone_app_state`; optional app inactivity needs usage access. Locked-user and unavailable results remain unknown. It does not grant another app's private files or screen content. |
| All-files access | Functional shared-storage tools `phone_files_list`, `phone_files_read`, `phone_files_write` use this actual grant on Android11+. Android8–10 requires the relevant ordinary READ/WRITE storage grant and actual OS access; scoped-storage restrictions still apply. Tools accept only relative paths under the shared external root and reject traversal/symlink escape. Android/data and Android/obb are attempted only within that root and remain inaccessible whenever the OS denies them. Listing caps at100 entries, UTF-8 reads at50000 characters and1MiB input, atomic UTF-8 writes at100000 characters; tools do not recursively delete files. This is not root. Durable memory/files use private storage independently. |
| System settings | Brightness can be written after Write System Settings access. Secure/global settings are not claimed writable. Automatic brightness may override the written value. |
| Notification policy | Separately enabled Do Not Disturb policy access supports requested filter changes and relevant ringtone/volume changes. The observed global filter is returned separately because Android can apply app-specific policy behavior. |
| Overlays | Requested windows can be shown, updated and removed after actual overlay access. This does not grant screen capture or touch injection. |
| Vibration | Requested vibration uses the declared normal `VIBRATE` permission and available hardware. An accepted Android request does not prove that the owner felt it. |
| Battery exemption | Opens the system exemption list. This does not guarantee minute-by-minute execution, force-stop recovery, or unrestricted foreground-service time. |
| Exact alarms | `phone_alarm_schedule/list/cancel` use actual `canScheduleExactAlarms` and `setExactAndAllowWhileIdle` for requested native reminders. A durable schedule receipt precedes the Android call; a separate non-exported receiver records an actual callback before optional local notification. Registration acceptance never means the reminder fired or was seen. Cancellation preserves earlier firing evidence. Rebooted/restored requests are reported as unverified and are not replayed automatically. This does not invoke an AI or guarantee24-hour AI scheduling. |
| Legacy device admin | Required by the owner's setup on supported devices. `phone_device_admin_state` reports actual activation and granted force-lock policy; `phone_screen_lock` calls the corresponding Android operation and reports observed lock state separately. The manifest requests force-lock policy. Device/profile-owner management and lock-screen authentication are different Android capabilities. |

`PhoneTools(Context, HoyoungStore).catalog()` returns42 `{name,description,inputSchema}` tool definitions. `execute(String name, JSONObject args)` returns a JSON result with `ok`, `code` and bounded tool-specific data; failures provide a message where available. Unknown tools return `unsupported`; actual denials return `permission_missing` (with a `permissionId` when known). Clipboard reads require foreground state. `phone_url_open` accepts valid HTTP/HTTPS URLs only and asks Android's installed web handler to open them; it does not claim that a browser loaded the page or logged in. App-launch, asynchronous captures and gesture results distinguish a request accepted by Android from confirmed completion. Every tool checks relevant Android permissions again when invoked; the runtime separately checks editable per-tool allow settings. Shared-file paths/content enter only a requested Work result, not a background inventory upload.

`phone_contact_get` reads source-backed name, phone, email, address and organization fields with a raw-contact ID. `phone_contact_update` explicitly updates a selected raw contact and discloses that all existing values of each requested field kind are replaced. `phone_calendar_update` changes one explicit event and requires paired start/end times when changing its schedule. Contacts and calendar content observers record change notices and deduplicate bounded snapshots; they do not falsely claim a complete address-book or calendar export.

`PhoneContextCollector(Context, PhoneTools, HoyoungStore)` is started by the runtime's visible autonomy service. Call `start()`, `stop(reason)`, `reconcilePermissions()` on resume/pulses, and `sampleNow()` on each service pulse. `state()` reports collector/journal/sensor health; `relevantContext(query,maxChars)` selects bounded relevant observations with provenance and current source permissions. The collector never initiates cloud requests. `phoneContextEnabled` defaults to true and can stop collection; per-source `toolPermissions` additionally apply. `phone_context_read` pages or retrieves an explicit event ID; `phone_context_search` searches the durable archive instead of only a recent cache.

Android notification, sensor and provider callbacks first write a private `files/device-journal/pending` record with source, original content, observation/capture times, deduplication key and checksum. The file is flushed with `FileDescriptor.sync()` and atomically renamed before a receipt reports `observationPersisted:true`. This receipt is distinct from a confirmed SQLite event ID: one background worker indexes the observation, and SQLite's deduplication key prevents a crash between commit and acknowledgement from creating duplicate events. Callback writes and small collector state files do not acquire the database monitor, so streaming backups cannot hold them behind a long database lock. Successful indexing moves the immutable original into the private `archive` tree; it does not silently delete raw observations. Corrupt or rejected originals remain in `quarantine` with explicit gap events. Interrupted complete writes are recovered on restart. An oversized record or failed write reports an error; a small failure marker is persisted when storage permits, and the next successful write records the gap. A completely full or unavailable disk can also prevent the gap marker from being saved; file flushing does not promise recovery from every hardware or filesystem failure.

Source visibility uses current Android grants and current app flags even for historical events. `PhoneTools.canReadStoredSource(JSONObject deviceEvent)` is the shared filter for retrieval of device events and memories derived from them. Owner setting changes call `applyPermissionPolicyFromOwner(toolPermissionsJson, phoneContextEnabled)` immediately after saving, so a sensor/notification/voice callback cannot keep using an old permission cache; an older background settings read cannot undo the revocation. Background policy refresh and cloud retrieval run away from Android callback threads.

`PhoneTools.canReadArchivedToolResult(toolName, result)` also gates old action receipt bodies and immutable native-result artifacts. It checks current feature flags and actual grants, including each event source in a context result. Clipboard history requires actual foreground state. A current selected-media-only grant cannot prove all old media items remain selected, so those old results require a current full-library grant; a new live bounded query can establish the current selection. Unredacted historical Wi-Fi identifiers recheck Wi-Fi and location grants. Unsupported/unverified sources remain hidden without deleting their local originals. Observation-derived location/contact/calendar/notification/activity/usage/microphone results stay hidden when global phone observation context is disabled; explicit UI/file results additionally require their own current special access.

Raw acknowledged observations are compacted by the background ingestion worker into immutable segments capped at32MiB, typically grouping256 original files across days. Each frame retains the original filename, exact bytes and SHA-256; the segment has a verified content hash. Publication, file/directory flushing and verification finish before matching originals are unlinked. Snapshot pins prevent compaction from deleting files still being captured. Exports also pack an old uncompacted backlog, avoiding one ZIP entry per archived event. This reduces inode overhead without deleting observations or promising a fixed annual storage size. The current expanded backup limit is4GiB. See [device-journal format and recovery](android-device-journal.md).

Backup registration uses an `InternalFiles.BackupParticipant` with `capture(destination)` calling `PhoneEventJournal.captureBackupSnapshot(context, destination)` and `validate(stagedJournal)` calling `PhoneEventJournal.validateBackupSnapshot(stagedJournal)`. The private journal snapshot precedes the database cut; immutable hardlinks or open-file copies survive ingestion moves. Pending files, raw archives, state and quarantine travel with the checksum-validated backup. Published segment framing and hashes are validated in staging before any live namespace/database replacement. For replacement, stop the collector and captures, call `PhoneTools.pauseForBackupRestore()` on the background restore thread, perform restore, then call `PhoneContextCollector.afterBackupRestore()` in `finally` for success or failure. This barriers in-flight ingestion, blocks collection during replacement and reloads restored state. Legacy backups without device-journal files safely recreate directories. Acknowledged archive segments never replay as pending observations. Automatic execution stays paused for owner review after restore.

Accessibility window identity is checked when Android exposes window IDs, and stale node IDs cannot receive clicks or typing. The assistant's own UI can be operated through the same tools as other apps; generated chat input and settings changes retain agent provenance instead of being attributed to a real owner gesture or instruction. This provenance changes attribution, not tool permission.

Own reply notifications retain `sourceKind:assistant_reply`, assistant message ID/stage and `ownerReadConfirmed:false`; notification display is not an owner instruction or confirmed read. External packages copying the extras cannot claim assistant identity. `PhoneTools.canUseImplicitMemorySource(event)` applies current grants/flags and excludes actual own reply-display events from implicit memory/proactive context; `canReadStoredSource` and explicit archive reads remain available. This prevents assistant output from feeding back as new external input without deleting history.

Activity monitoring uses real `TYPE_STEP_COUNTER`, with `TYPE_STEP_DETECTOR` fallback. Counter values are steps since reboot while the sensor was active, not an invented whole-day total. Samples aggregate actual deltas, include boot resets and observation gaps, and stop/unregister on permission or feature revocation. The collector flushes pending samples on its pulse and stop. It does not record raw accelerometer streams or infer walking/driving/sleeping classes from a step counter. Android's official descriptions explain [counter latency and required ACTIVITY_RECOGNITION access](https://developer.android.com/develop/sensors-and-location/sensors/sensors_motion), [usage-history availability and bucket coverage](https://developer.android.com/reference/android/app/usage/UsageStatsManager), and [foreground/background location access](https://developer.android.com/develop/sensors-and-location/location/permissions).

On Android13 and later, a sideloaded APK can face **Restricted settings** when enabling accessibility or notification access. The OS may require the user to open Settings → Apps → 호영 → the app-info overflow menu → **Allow restricted settings** (제한된 설정 허용), then return to the special-access screen. Exact menus depend on the manufacturer and installation method. This is an Android step that the app cannot approve for the user; it does not mean another app login or developer confirmation is required. See [Google's official restricted-settings instructions](https://support.google.com/android/answer/12623953?hl=en).

App inventory depends on Android package visibility. `QUERY_ALL_PACKAGES`, if declared for the personal assistant's installed-app management feature, remains subject to distribution-store policy review. A normal installation does not acquire root, system-signature permissions, device-owner status, another app's credentials, or perpetual operating-system execution rights.

Development validation must not read real users' contacts, notifications, location, clipboard or private app data, and must not place calls, send messages or purchase anything. Shared-file and device-context Robolectric tests use synthetic storage, notification, sensor, usage and location inputs, covering durability beyond the old ring, paging/search provenance, grant revocation, step resets/aggregation and stale-location reporting. Journal tests additionally cover a database blocked during callback writes, commit-before-ack crash replay, corruption quarantine, pending/archive backup snapshots, interrupted renames, persisted failure gaps, stale policy-read races and replacement barriers. Compile/manifest checks cannot prove Samsung sensor delivery, battery behavior, foreground/background wake frequency, microphone/camera capture, or Settings grant screens. Those require explicit on-device verification after installation. Observation gaps remain visible; no24-hour uninterrupted capture or exact annual storage size is promised.
