# 365회 개인 비서 기억 시뮬레이션

실제 `HoyoungStore`, `MemoryRetriever`, `MemoryReviewCoordinator`로 날짜를 가진 가상 사용자 세션 365개와 방해 기록 30,660개를 누적했다. 질문은 매 checkpoint마다 간식 금기·음료·배송 주소·공식 이메일 말투·연락 시간·비용 한도·주소록 공유·옛 물건·초기 접수번호·프로젝트 상태/담당자/장소/별명·정기 회의·식단·GPS 관측·없는 여권 번호 등 24개다. 단순 row 수가 아니라 현재 적용할 값, 이력이 현재 값으로 혼동되지 않는지, 실제 source/hash, 전달된 12,000자 문맥 안의 근거, 가상 행동 계획을 검사한다.

**요약·별명·검토 결정과 행동 판정 규칙은 사람이 작성한 시험용 정답이다.** 실제 모델이 1년간 정보를 추출하거나 사용자를 학습한 실험이 아니다. 임베딩·실제 LLM 답변·휴대폰 지연·장기 배터리는 측정하지 않았다. 365개 날짜는 fixture 생성 시 기록 시간을 지정하고 production의 record hash를 다시 계산했으며, source를 연결한 이후 원문과 hash를 바꾸지 않았다. 실제 365일이 경과했다는 뜻은 아니다.

| 누적 세션 | 방해 기록 | 시나리오 통과 | 현재 조건 | 초기 raw-only 필드 질문 | 가상 행동 판정 | query 중앙값 / P95 |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 84 | 24/24 | 19/19 | 2/2 | 9/9 | 70 / 194 ms |
| 30 | 2,520 | 24/24 | 19/19 | 2/2 | 9/9 | 35 / 313 ms |
| 180 | 15,120 | 24/24 | 19/19 | 2/2 | 9/9 | 192 / 611 ms |
| 365 | 30,660 | 24/24 | 21/21 | 2/2 | 9/9 | 390 / 1,725 ms |

초기 raw-only 2/2는 접수번호와 신발 크기라는 **두 필드에 대한 질문 두 개**이며, 둘 다 첫날 사용자 메시지 **한 원문**에 들어 있다. 서로 독립된 원문 두 개의 회상으로 세지 않는다. 두 필드에는 derived note를 만들지 않았고, 각 질문에 같은 day1 원문의 정확한 ID/hash와 필요한 값이 실제 bounded context에 전달되는지 확인했다.

각 단계의 current note와 source/hash 참조는 모두 유지됐고, 365개 사용자 원문의 내용·문자 수·raw hash·record hash가 끝까지 일치했다. 주소/음료/회의/비용/연락 시간의 정정과 과거 주소의 as-of 조회를 구분했다. 210회차에 알려준 프로젝트 별명은 그 전에는 근거가 없었고 마지막 단계에서는 담당자와 장소에 연결됐다. 이것은 올바르게 저장한 새 별명 때문에 답할 수 있는 질문이 늘어난 결과이며 모델 자체의 학습 정확도가 올라갔다는 증거가 아니다.

180회차에 GPS visibility predicate를 false로 바꾸자 original과 그에 연결된 derived note가 함께 사라졌고 GPS 범위 질문은 근거 부족으로 처리됐다. 실제 Android 설정의 권한 철회 실험은 별도 테스트다. 원래 알려준 적 없는 여권 번호도 근거를 만들지 않았다. 가상 행동 판정은 땅콩·육류 배제, 02시 연락 유예와 07/08시 구분, 0/15,000원 한도에서 12,000원 비용의 범위 구분, 주소록 전송 금지, 완료 **보고**를 독립 완료 증거로 바꾸지 않고 재실행하지 않기 등을 확인했다. 실제 결제·전송·주문은 하지 않았다.

최종 DB+WAL은 약 22.6 MB이고 note 1,551개다. 대부분 짧고 반복적인 방해 기사이며 실제 사진·긴 코드·모델·vector/ANN 파일을 포함하지 않는다. 따라서 “실사용 1년에도 20 MB면 모든 기억이 충분하다”라는 주장을 뒷받침하지 않는다. 핵심 사실 상당수가 첫 세션 한 원문에 모여 있고 별명/검색어와 pinned 설정을 수동으로 넣었으므로, 이 96개 통과를 전체 실세계 대화의 100% 회상으로 일반화할 수 없다.

문맥 크기는 모두 12,000자 이하였다. 넓은 질문은 candidate limit에 도달했고 데이터가 늘수록 검색 비용이 증가했다. 이 실행은 다른 개발 작업과 공유한 호스트에서 수행했으므로 표의 지연은 휴대폰 성능이나 엄격한 최악 한도가 아니다. 결과는 저장·정정·source 접근·문맥 예산의 회귀 검증이며, 추출 누락·다양한 실제 표현·장기간의 사용성은 추가 검증이 필요하다.

재현은 `HOYOUNG_LONGITUDINAL=1`로 `LongitudinalMemoryProductBenchmarkTest`를 별도 실행한다. 기본 unit suite에서는 이 비교적 무거운 simulator를 건너뛴다. `HOYOUNG_LONGITUDINAL_OUTPUT`을 지정하면 실제 검색 결과를 `report.json`과 `contexts.jsonl`로 저장한다. 독립 reader에게는 `fixtureOracle` 필드를 제거한 JSONL을 전달하고 정답은 별도 파일로 보관해야 한다. 시험 결과와 source SHA는 [benchmark receipt](benchmarks/longitudinal-memory-product.json)에 있다.

## 선택된 문맥의 독립 모델 독해

12개 시나리오를 첫날·365회차로 짝지은 24개의 실제 검색 문맥을 별도 협업 모델에 전달했다. reader는 다른 에이전트 대화와 정답표를 받지 않았으며 입력에서 `fixtureOracle`도 제거했다. 요청 모델은 GPT-6.1 Sol·Medium이고 실제 backend·Fast·과금 telemetry를 독립 확인한 시험은 아니다. 앱→실계정 Work 연결을 실행한 것도 아니다.

부모 에이전트가 답변 24개를 각각 읽고 현재/옛 선호와 주소, 연락 시간, 예산, 초기 접수번호, 나중에 배운 프로젝트 별명, 완료 보고의 미검증 상태, GPS의 과거 관측과 현재 위치 차이, 없는 여권 번호에 대한 유보를 수동 평가했다. 이 선택된 rubric은 24개 모두 충족했다. 인용 23개는 모두 해당 케이스에 전달된 문맥에 정확히 존재했다. 인용 문자열 일치는 의미적 진실의 독립 검증이 아니며 정중한 문체로 답한 reader의 호영 말투·자율성·경쟁 제품 우위는 평가하지 않았다.

첫날 모르는 새 별명을 마지막 단계에서 연결했고, 바뀐 현재 값을 옛 사실과 혼동하지 않았다는 좁은 결과다. 사람 손으로 만든 기억 메모·선별 질문·제공 문맥에 대한 독해이므로 실제 1년 자동 추출, 모든 질문의 검색 성공, 100% 기억 정확도는 증명하지 않는다. 합성 원문만 담은 [reader 입력](benchmarks/longitudinal-blind-reader/reader-inputs.jsonl), [원래 응답](benchmarks/longitudinal-blind-reader/reader-output.json), [평가 범위·해시](benchmarks/longitudinal-blind-reader/receipt.json)를 함께 보관한다.
