# 호영 모바일 비서의 사용자 흐름 검증

목표는 개별 오류 수정이 아니라 사진·파일이 있는 대화, 빠른 새 입력, 하루 동안 맡긴 일의 진행, 휴대폰 관찰, 장기 개인화가 한 흐름으로 이어지는 것이다. 제품의 기본 운영 조건은 추가 유료 API·사설 VM·상시 PC 없이 Android 앱과 ChatGPT Work 임시채팅을 사용하는 것이다. Dot보다 우수하거나 완벽하다는 비교 평가는 아직 수행하지 않았다.

## 대화·모델·미디어

| 사용자 흐름 | 현재 동작 | 확인한 증거와 남은 범위 |
|---|---|---|
| 글을 쓰고 사진·파일을 붙인 뒤 앱을 나간다 | 원자적 draft의 텍스트·첨부·입력 ID·revision을 보존한다. 이미 큐에 저장한 보내기는 같은 ID로 중복 접수하지 않는다. | draft 24개와 입력 identity 18개 회귀. 실제 Android 재시작 검사는 별도 결과에 기록한다. 가져오기 도중 OS가 프로세스를 죽인 URI 작업 전체의 복구를 보장하지 않는다. |
| 큰 사진을 보내고 다음날 그 내용으로 대화한다 | 원본을 불변 저장하고, 필요하면 작은 Work 전송 사본을 만든다. 분석 기억에 원본 ID·SHA와 전달 표현 SHA·분석 범위를 연결한다. | 실제 11 MiB PNG→JPEG→접수→분석의 native 통합 9개 통과. 모델이 원본 전체를 읽었다는 주장을 보내도 native 검증 값은 false로 남는다. 실계정 업로드는 미검증. |
| 영상·음성·문서·ZIP·일반 바이너리를 전송한다 | 원본을 유지하고 허용된 파일 입력에 정확한 바이트를 전달한다. 허용하지 않는 형식·크기나 불명확한 업로드는 파일을 빼지 않고 요청 전체를 멈춘다. | native exact-byte 검사와 Chromium File/DataTransfer 검사를 분리한다. Work 자체의 모든 확장자·미디어 이해 지원을 보장하지 않는다. 전송은 파일당 10 MiB·합계 20 MiB·최대 8개이며 큰 비이미지의 분할 업로드는 현재 구현하지 않았다. |
| 모델·추론 수준·속도를 바꾼다 | 설정 및 대화의 앱 설정 도구로 요구값을 저장하고, Work 화면에서 실제 선택된 값과 대조한다. 기본값은 GPT-6.1 Sol·Medium·Fast다. | 요구값 변경·잘못된 설정의 원자적 거부·유사 이름·업로드 중 선택 변경 회귀. 모델 메뉴 조작은 Work 화면에서 사용자가 수행하며, 설정 저장만으로 서비스의 실제 선택이나 이용 가능성을 증명하지 않는다. |
| 이전 작업 중 새 지시를 보낸다 | 새 원문을 먼저 저장한다. 아직 시작하지 않은 이전 폰 도구 제안은 보류하고 새 입력을 우선 처리한다. | 실제 SQLite·파일 잠금/latch·입력 cohort 회귀. 이미 실행한 OS 효과의 취소, 클라우드 native steer의 실계정 작동은 확인하지 않았다. |

큰 원문을 UI에서 전부 읽지 않는다. 대화는 40개·각 8,000자 페이지로 읽고 전체 원문은 별도 열람한다. 사진의 메모리·worker·대기열도 제한한다. 파일 목록과 사진 준비는 UI와 별도 worker에서 처리한다. 파일 목록은 최근 100개와 파일명 검색을 기본으로 하며 정확한 선택 확인은 전체 폴더 재탐색 대신 해당 원본 메타데이터를 직접 조회한다.

일반 대화·도구 후속 응답에는 미검토 원문 60,000자를 덧붙이던 경로를 제거했다. 누락된 원문은 삭제하지 않고 별도 기억 검토에서 12,000자 이하로 진행한다. 이는 로컬 준비량을 줄이는 개선이며 실제 Work의 모델 첫 응답 시간이나 네트워크 속도를 측정한 결과는 아니다. 요청 준비 시간과 전송 후 대기 시간을 구분해 상태에 표시한다.

0.3.0의 첫 자율 판단에는 최대 6,000자의 직렬화된 기억 검토 배치를 함께 넣는다. 현재 입력·권한·제약의 필수 문맥이 먼저 보존되며 검토가 들어가지 못하면 미완료로 남긴다. 유효한 ACK만 실제 검토 진도로 반영하고, 완료한 배치를 도구 후속 요청에 다시 보내지 않는다. 별도 모델 호출을 추가해 이 기회를 만들지 않는다. 검토 원문·주변 문맥의 실제 hash와 출처 관계는 답변·영수증·다른 목표의 진행 기록까지 연결한다. 180개 관련 회귀는 실제 SQLite와 가상 시계의 검증이며, 모델이 항상 유효한 ACK를 반환하거나 실제 폰에서 24시간 실행했다는 증거는 아니다.

## 재부팅·오류·한도

최초 WebView 생성·설정·URL 로딩 실패와, 아직 어떤 문서도 로드하지 않은 renderer 종료는 한 개의 타이머로 1→5→30→60초 간격 재시도한다. 실제 문서가 열리기 전에는 재시도 이력을 초기화하지 않는다. 앱의 대화·원문 저장은 유지하며 로딩·다음 재시도·준비 미완료 상태를 보여 준다.

이미 열린 문서나 접수된 작업의 renderer 종료는 단순 초기 로딩 실패와 다르다. 기존 결과를 잃은 상태를 보존하고 자동으로 새 임시 대화를 열거나 같은 작업을 재전송하지 않는다. provider 오류가 선택·취소·재확인·권한 전달의 main callback에서 발생해도 앱 프로세스에 예외를 그대로 던지지 않는다. 새 시작/복구 회귀는 12개이며 최종 전체 Android 실행 기록은 빌드 증거에 연결한다.

일반 재부팅의 BootReceiver, 프로세스 crash의 foreground service 복구, 사용자의 Android **강제 중지**는 별도 시험이다. 강제 중지된 패키지는 사용자가 다시 열기 전 OS가 자동 시작을 제한한다. 삼성의 배터리·백그라운드 정책, 폰 전원·통신, WebView와 서비스 가용성에 따라 24시간 연속 관찰이 중단될 수 있다. 이를 앱 내부의 작업 기록 보존과 혼동하지 않는다.

실제 한도 안내를 관찰하면 앱 자체 답장과 대기 상태를 보존한다. 유료 API나 자동 크레딧 구매로 바꾸지 않는다. 전송 여부가 불명확한 부작용 작업은 한도 해제나 재시작만으로 반복하지 않는다. 읽기 전용 도구 실패는 typed 실패 영수증으로 남겨 다음 조회·새 요청을 계속하고, 쓰기 결과가 불명확하면 확인 대기를 유지한다.

## 휴대폰 정보·장기 개인화

알림에서 실제로 관찰한 제목·본문·큰 본문·대화 메시지·이력을 bounded 원문으로 보관하고 SHA·누락/제한 여부를 표시한다. 자기 앱의 답장 및 foreground service 알림은 암묵적인 개인화 입력에서 제외한다. 실제 연락처·일정·위치·활동·앱·알림·접근성 도구는 OS 허용 상태와 앱 도구 설정을 실행 시 다시 확인한다. 과거 위치를 현재 위치로 추정하지 않으며 권한을 철회한 관찰과 연결 메모는 자동 문맥에서 제외한다.

백그라운드 주소록/일정 snapshot은 제한된 관찰이다. 주소록 전체를 이미 읽었다고 주장하지 않고 요청별 검색·상세 조회로 필요한 근거를 보충한다. 일반 앱이 갖지 못하는 root·시스템 서명·기기 소유자 권한을 얻었다고 표시하지 않는다. 요청하는 기본 권한 40개와 알림 접근·접근성 등 특수권한을 유지한다.

원문은 요약과 별도로 남고, 기억은 원문 ID·정확한 인용·hash·시점·정정 revision·별명·중요도에 연결된다. 사용자 사실과 장치 관찰, 모델이 만든 분석·추론·실행 교훈은 구분한다. 실행 교훈은 개인 결과값을 제외한 작은 native system 원문을 인용할 수 있지만 사용자 사실·선호로 승격하지 않는다. cache·모델·ANN graph는 원문의 권위 있는 기록을 대체하지 않는다.

장기 사용 시험은 [365회 가상 세션](longitudinal-memory-product-benchmark.md), [백만 합성 원문과 공개 검색 자료](memory-research.md), [실제 모델 추출 probe](model-memory-evaluation.md)로 구분했다. 선택된 독립 reader 24개 답변도 원본 입력·응답·수동 rubric을 공개한다. 실제 1년 자동 추출이나 모든 질문의 정확도가 늘어난다는 보장은 하지 않는다. 검색 지연의 증가와 candidate cap도 측정 결과에 남긴다.

사용자가 지정한 「세션과 기억처리」 원문은 2026-10-13 22:33 UTC에 공식 Space 목록·본문·전체 커서와 공유 링크를 다시 확인했으나 읽을 수 있는 Library 파일 참조를 확보하지 못했다. 따라서 그 문서를 전부 반영했다는 주장은 하지 않는다. 현재 구현은 확보된 사용자 요구와 1차 연구를 기준으로 한 독립 구현이다.

## 배포 판정

각 체크포인트에는 같은 소스의 전체 unit suite·lint·APK 빌드·Chromium 브릿지 결과, 실제 AOSP Android UI/파일/provider/native 검사와 프로세스·재부팅 검사를 연결한다. synthetic 모델/transport 검사, 실제 Android 검증, 실계정 Work와 S24 Ultra 실사용은 서로 대체하지 않는다. 실패를 숨기거나 assertion을 낮춰 배포 통과로 만들지 않는다. 최종 APK는 기존 release와 같은 개인키로 서명하고 권한·native ABI·16 KiB 정렬·source commit·SHA를 확인한 뒤 공개한다.
