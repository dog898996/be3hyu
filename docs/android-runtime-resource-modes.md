# Android runtime resource modes

The editable setting `wakeMode` accepts exactly `continuous`, `while_working`, or `charging`. Existing Android permissions remain declared and independently controlled. This setting changes CPU wake-lock use; it does not grant a permission, bypass battery restrictions, create a private cloud server, or guarantee an uninterrupted Work connection.

| Mode | Actual behavior |
|---|---|
| `continuous` (default) | The visible autonomy service renews a120-second non-reference-counted partial wake lock on its60-second local pulse. While the service and leases keep running, the CPU remains awake between pulses. This preserves the owner's priority for continuous operation and uses more battery. |
| `while_working` | A local pulse uses a short bounded lease. Preparation, dispatch, an active Work request, completion processing, or queued/running local collector work can retain a120-second lease. The service releases it once those operations finish. While idle, the CPU may sleep and subsequent Handler pulses may be delayed. |
| `charging` | Uses `continuous` while Android reports an actual power plug, including a plugged-in full battery. On unplugging, it switches to `while_working`; it does not claim wireless/USB/AC power merely from a charging UI label. |

Owner setting changes and runtime work-state changes call `AutonomyService.reevaluateActiveService()`. This only posts to an existing service's main Handler; it never starts a new background service. Battery-change broadcasts and local collector completion also reevaluate the lease. Service stop releases the wake lock and unregisters its receiver. Invalid restored enum text is surfaced as `validConfiguredWakeMode:false` with the existing `continuous` default, rather than silently inventing a fourth policy.

`AutonomyService.resourceState()` is cached and does not query the database. It includes configured/effective modes, actual plug state, actual wake-lock held state, last local pulse time/delay, device idle/power-save state, current battery-exemption state and explicit `timing:"best_effort"` and `batteryCostMeasured:false`. Delay detection uses elapsed realtime, which includes CPU sleep, with wall time as a restart fallback. An interval exceeding65 seconds or an elapsed-clock reset records a source-backed scheduler gap. The gap is an observed scheduling delay; it does not invent what happened while the app was asleep.

The local60-second pulse and AI heartbeat are different. The former collects bounded observations and checks the queue; the latter defaults to300 seconds and only runs when authenticated Work is ready, quota is available and no uncertain or active request blocks it. No accumulated missed intervals are replayed as a burst of duplicate AI turns. Android `Handler.postDelayed` uses uptime, so deep sleep adds delay. A wake lock can also be ignored by Doze without an applicable exemption, and even an exemption does not provide force-stop recovery or perpetual execution. Android's periodic WorkManager minimum is15 minutes; idle-allowed alarms are also throttled during Doze. Neither is an exact one-minute replacement.

No Samsung battery percentage, temperature, daily lifetime or uninterrupted24-hour performance has been measured. Synthetic tests verify policy transitions, idle release, plug/unplug handling and stop cleanup. Actual Galaxy S24 Ultra screen-off/Doze/battery-exemption behavior, Work WebView continuity and hardware sensor delivery still need on-device observation. Battery exemption and wake modes are owner-controlled settings; the app does not toggle Android protections itself.

## Location coverage

The current collector stores changes in sufficiently recent cached `LocationManager` readings, with a default15-minute maximum age. It does not start continuous GPS, construct an unobserved route or know every place the owner visited. Individual source records retain provider, location-fix time, capture time, accuracy, age, mock flag and cache status. A bounded `phone_location_refresh` explicitly requests a fix, rejects invalid coordinates/accuracy and fixes exceeding its `maxAgeMs` (default60 seconds, maximum15 minutes), and admits that Android may return a recent cached fix. Timeout, revoked permission, invalid/stale fix and process interruption remain unsuccessful or uncertain receipts with observation gaps.

Foreground-only permission does not authorize arbitrary screen-off/background location use. The existing `specialUse` service is not a `location` foreground service. A background grant alone also does not make route history complete: Android8+ limits background location delivery, providers can be unavailable, and a sleeping/stopped process can miss callbacks. UI and model output should show the latest observed fix time, accuracy, cached versus requested status and missing coverage instead of labeling this a complete location history.

An additive improvement can register `LocationManager.PASSIVE_PROVIDER` with actual read/background grants, live per-source app flags and a visible collector. This receives location generated by other applications rather than powering GPS for every pulse. Records should deduplicate by actual fix time/provider/coordinates, include accuracy and uncertainty, use the durable observation spool and stop immediately on grant or feature revocation. Passive delivery still cannot guarantee coverage. Explicit navigation/route tracking would need a separate visible location feature, the correct `location` foreground-service type and permission, legitimate foreground-service startup, clear user control and bounded update policy. It should remain separate from the default cached/passive context collector.

## Phone capability limits

SMS and call-log declarations are installer/role restricted; a normal personal APK is not automatically an SMS/default-dialer handler. The current build opens the dialer and reads granted call state, and ships no automatic SMS sender or direct-call tool. All-files access does not expose other applications' private directories, `Android/data`, or `Android/obb`. Writable System settings do not grant Secure/Global settings. Accessibility cannot grant permissions, operate protected permission/settings/installer screens, read password input or act as root. Legacy device administration is not device-owner status. Permission and tool descriptions must report these real boundaries.
