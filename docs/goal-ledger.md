# 미완료 목표 원장

Work 응답 한 턴이 끝난 것과 사용자가 맡긴 목표가 완료된 것은 다르다. `GoalLedger`는 후속 확인이 필요한 목표를 `activeGoal:<rootRequestId>` 설정에 따로 저장한다. 실제 요청·원문·종료 기록은 기존 요청과 이벤트 저장소에 보존한다. 앱 프로세스가 바뀌거나 백업을 복원해도 활성 목표를 다시 읽을 수 있다. 활성 목표의 변경·종료마다 `goalLedgerRevision`을 같은 트랜잭션에서 갱신하므로, 런타임은 준비 중에 목표가 바뀐 프롬프트를 전송 전에 폐기할 수 있다.

## 저장과 출처

활성 상태는 `queued`, `working`, `awaiting_result`, `blocked`, `uncertain`이다. 레코드는 원 요청 ID, 실제 사용자 원문 ID, 마지막 요청 ID, 보고된 단계, 진행 설명, 생성·갱신 시각, 다음 확인 시각을 가진다. 사용자 원문은 실제 `user` 메시지이며 해당 원 요청에 속해야 한다. 출처를 바꾸거나 관계없는 요청을 후속 작업으로 연결할 수 없다. 사용자 발화가 없는 자율 목표는 실제 `autonomy` 요청이 있을 때만 만들 수 있다.

활성 목표는 최대 256개다. 한도를 넘으면 `goal_capacity_reached`와 한도·정리 필요 메시지를 반환한다. 기존 목표를 조용히 삭제하지 않는다. 원 요청은 남아 있으므로 추적 실패를 사용자에게 표시하고 원장을 정리한 뒤 다시 연결할 수 있다. 닫힌 목표는 활성 설정에서 제거하되 `goal_closed` 또는 `goal_owner_resolved` 이벤트에 마지막 상태를 남긴다.

## 완료의 의미

이미 추적 중인 목표에 모델이 `completed`를 보고해도 실제 완료 근거가 없으면 `awaiting_result`를 유지하고 `reportedStage:completed`, `completionVerified:false`를 남긴다. 첫 일반 대화의 정상 완료는 불필요한 목표를 만들지 않는다. 신뢰할 수 있는 런타임이 실제 영수증에서 `completionVerified:true`와 `verificationSource`를 제공하면 목표를 닫는다. 이 근거는 모델 JSON이 스스로 선언한 값을 그대로 사용해서는 안 된다. 영수증이 검증한 범위보다 강한 목표 완료를 주장해서도 안 된다.

모델이 기존 목표를 포기하겠다고 말하면 목표를 `blocked`로 남긴다. 사용자에게 종료 또는 제외를 명시적으로 요청받은 호출자만 `resolve()`나 `remove()`를 사용한다. 사용자 확인으로 추적을 끝낼 때도 외부 서비스 결과가 독립적으로 검증되었다고 기록하지 않는다. 이 API는 호출자가 실제 사용자 요청을 확인했다는 전제이며, 모델이 임의로 사용자 승인을 만들어서는 안 된다.

## 완료 보고의 운영상 보관

매번 완료된 로컬 작업까지 영구히 대기 상태로 남기면 256개 슬롯이 차고 사용자가 모든 일상 작업을 수동 종료해야 한다. `archiveReportedCompletion`은 실제로 관찰·저장한 공급자 완료 보고를 `reported_completed`로 보관하여 활성 슬롯을 회수한다. 이는 `completed`의 실제 목표 검증과 다른 단계다. `completionVerified`, `overallOutcomeVerified`, `providerOutcomeVerified`는 모두 `false`이며 `mayAutoRepeat`도 `false`다. 보관 API의 `completionConfirmed:true`는 `confirmationScope:goal_ledger_archival_only`, 즉 원장 보관 변경만 확인한다.

호출자는 실제 저장된 요청의 응답 해시·상태와 실제 네이티브 영수증에서 요약을 만든다. 진행·결과 미확인, 실패한 변경, 미확인 변경, 손상된 영수증, 사용자 중지 또는 차단·불확실 목표가 있으면 보관하지 않는다. 읽기만 하는 도구의 오류는 진단으로 보존할 수 있다. 같은 이름의 변경을 나중에 성공했어도 과거 실패를 자동으로 해결된 것으로 추정하지 않는다. 보관 직전 같은 트랜잭션에서 영수증의 정렬된 키·원문 해시 스냅샷을 재검사하여 이전 요약으로 바뀐 결과를 처리하지 않는다.

네이티브 영수증이 없거나 모두 확인되었다는 사실만으로 클라우드 작업이나 사용자가 요구한 모든 조건이 달성되었다고 말할 수 없다. 순수 클라우드·혼합 작업도 공급자의 보고라는 범위로만 보관한다. 원래 활성 레코드의 정확한 문자열, 보고, 네이티브 요약은 새 불변 시스템 원문에 저장하고 이벤트·원문 해시를 남긴다. `goalReportedArchive:<rootRequestId>`에는 작은 조회 인덱스만 저장한다. 자율 점검에서 다른 기존 목표를 보고할 때도 실제로 관찰된 해당 보고자 요청의 해시를 남겨 생산자를 추적한다.

`list(scope:'reported_archive')`는 보관 인덱스만 페이지로 조회한다. 원문 ID·해시, 보고자 요청·응답 해시, 네이티브 범위와 미검증 표시를 반환한다. 조회는 원문 레코드의 참조 해시를 확인하며 매번 원문 파일 전체의 내용 검증을 수행했다는 뜻은 아니다. 필요한 전체 보고는 원문 읽기 도구로 검증·조회한다. 활성 조회의 기본 동작은 바뀌지 않는다. 300개의 일상 작업 보관과 한 개의 미확인 변경 목표를 함께 검증하여, 실제 대기 목표를 지우지 않고 슬롯을 재사용하는지 확인한다.

## 다음 행동과 조회

목표 원장을 읽는 행위는 작업을 실행하거나 다시 대기열에 넣지 않는다. 모든 레코드의 `mayAutoRepeat`는 `false`다. `blocked`와 `uncertain`은 사용자 확인이 필요하며 자동 재시도하지 않는다. `nextCheckAt`은 상태를 확인할 시각이고 행동을 다시 실행하라는 승인이 아니다. 진행 중이거나 결과를 기다리는 목표에만 읽기 확인 가능 상태를 표시한다.

`list()`는 `afterRootRequestId`, `limit`, `stage`, `dueBefore`를 지원한다. 설정 키의 인덱스 범위 `activeGoal:` 이상 `activeGoal;` 미만을 조회한다. 전체 설정·옛 종료 기록을 매번 훑지 않는다. 필터 결과가 비어도 실제 읽은 마지막 키로 다음 페이지가 진행된다. 읽을 수 없는 레코드는 삭제하지 않고 오류 개수와 ID를 반환한다.

레코드는 32,768자·중첩 64단계 이하의 완전한 JSON 객체와 필수 출처·시각 형식을 검증한다. 빈 저장값, 후행 데이터나 손상 값을 없는 목표로 취급하지 않는다. 손상된 슬롯을 사용자가 명시적으로 종료하면 정확한 원래 문자열을 새 불변 시스템 원문에 보존한 뒤 그 슬롯만 제거하고 리비전을 갱신한다. 원래 작업 결과나 출처를 복구했다고 주장하지 않으며 `previousGoalUnreadable`, `sourceUnknown`, 완료 미검증을 남긴다. 원문 보존·슬롯 제거·종료 이벤트는 같은 DB 트랜잭션으로 처리한다.

`context(maxChars)`는 최대 256개의 활성 레코드를 인덱스 페이지로 읽고, 현재 확인 시각이 된 목표를 우선한다. 첫 100개 뒤에 있는 목표도 후보에 포함된다. 실제 JSON 길이를 넘는 레코드는 전달하지 않고 `truncated`와 전체·표시 개수를 반환한다. 원 요청의 긴 본문은 짧은 발췌와 `sourceMessageId`로 제공하며, 필요한 본문은 원문 읽기 도구로 확인해야 한다.

## 검증 범위

테스트는 프로세스 재시작, 백업 복원, 잘못된 출처와 후속 요청, 모델의 미검증 완료, 실제 영수증 기반 종료, 사용자 종료, 차단된 목표의 재실행 방지, 필터 페이지 진행, 첫 100개 이후의 긴급 목표, 한도 도달, 손상 레코드, JSON 길이 제한을 확인한다. 실제 외부 작업의 목표 완료를 자동 검증하는 범용 기능은 아니다.
