# App permission policy audit

This audit separates the owner's editable tool settings, application-added restrictions, Android capability limits, and memory/execution integrity. The owner requested that the app stop imposing independent risk rules. The audit is based on production Java and Work-bridge code, not an assertion that a physical Samsung device accepted every action.

## Shared-file policy change

`PhoneSharedFiles.resolve` no longer categorically rejects `Android/data` or `Android/obb`. A shared-storage tool can attempt an OS-visible path when its current Android storage grant and per-tool setting permit it. Android 11+ scoped storage can still deny another application's directories; removing the application's ban does not confer root or override Android.

The shared-storage contract remains a relative path inside the actual shared external root. Canonical containment, traversal rejection and symlink handling ensure that `phone_files_write` cannot accidentally address the private canonical memory database or original attachment archive. These are storage namespace/integrity rules, not independent approval for a user-requested shared-file action. UTF-8 validation, atomic writes, truthful failure results and bounded read/list/write payloads remain.

`PhoneSharedFilesTest` uses Android 9/API 28 and synthetic files. It verifies allowed Android-directory writes, exact Unicode reads and listing, a failing write with an existing non-directory parent, storage-grant denial/revocation, malformed arguments, traversal, symlinks, invalid UTF-8 and oversized reads. A simulated OS-visible directory is not evidence that Android 15 grants access to another app's `Android/data` directory.

Focused verification on 2026-10-14: **10 tests, 10 passed, zero failures/errors/skips** with `testDebugUnitTest --tests com.hoyoung.assistant.phone.PhoneSharedFilesTest`. The final focused Gradle run completed successfully in 13 seconds. No real phone data was read or modified.

## Audit coverage and distinctions

| Area | Production implementation | Finding |
|---|---|---|
| Editable feature permission | `AssistantRuntime.executeTool`, `app.settings.update`, `PhoneEventJournal.toolAllowed` | Unspecified feature switches default to allowed. Explicit owner-disabled tools remain disabled. The AI can update available feature switches through `app.settings.update` when that tool itself remains enabled. A malformed settings record is a configuration error, not a granted permission. |
| All-permission onboarding | `PermissionOnboarding`, `MainActivity`, `AutonomyService` | The owner explicitly requested the setup gate. Actual applicable Android grants are rechecked; opening a settings screen is not a grant. Root/device-owner and installer/role-restricted grants cannot be invented. |
| Shared files | `PhoneSharedFiles` | Removed the application-added Android-directory category ban. Real storage grants and filesystem outcomes determine reachability. |
| Microphone | `PhoneVoiceRecorder` | Current tool captures 2–30 seconds while this app is foreground and stops after visibility/grant loss. This is the implemented capture capability; Android 15 background microphone support requires a correctly declared microphone foreground service and while-in-use/background-start eligibility. Deleting the foreground check alone would not implement that capability. |
| Calls, SMS and administration | `PermissionCatalog`, native phone tool catalog, device-admin policy XML | The available operations are reported by the actual native tool catalog and manifest. Installer/role-restricted permissions and device-owner/root are not acquired by an ordinary permission declaration. Granting a permission does not implement an absent operation. |
| Overlay and touch | `PermissionCatalog`, accessibility service XML and UI tools | Overlay grants allow drawing over other apps. They do not provide input injection or screen capture. The accessibility service supplies supported screen-tree/click/type/scroll/gesture operations after the actual accessibility grant. Android and the target app can reject protected actions. |
| Notification observation | `HoyoungNotificationListener`, `NotificationObservedContent` | Android-exposed text is archived with source and observation provenance. Android may redact or summarize it. Bounded/truncated fields explicitly disclose incomplete coverage. Owner-disabled collection and current source grants remain authoritative. |
| Work page and native bridge | `WorkWebController`, `work-bridge.js` | The Work transport and native dispatch bridge authenticate the current ChatGPT document, active request and origin. External pages must not manufacture Work responses or become owner-origin messages. Ordinary external browsing uses Android's browser handler. These bindings are transport integrity, not a claim that Android prevents browsing other sites. |
| Work-download hosts | `WorkingDownload.allowed`, Work download listener | The former application host allowlist has been removed. Valid HTTP/HTTPS file URLs and ordinary non-default ports are accepted when the owner enables `workFileDownloadsEnabled` (default true). Every redirect performs a fresh URL-scoped CookieManager lookup; a previous host's Cookie header is never copied to the destination. Actual Android cleartext-network policy still applies to HTTP. MIME/length checks and atomic writes remain correctness rules: an HTML login page or partial file must not be reported as a completed artifact. |
| Request loop limits | `AssistantRuntime` | The former hardcoded 24 tool rounds / 12 actions stop has been removed. `toolRoundLimit` and `toolActionsPerTurnLimit` default to zero, meaning no application count cap. The owner can configure positive integer caps, and a stop explicitly identifies the owner's configured limit. Source freshness, sequential receipts, steering, explicit pause and actual provider quota handling remain. |
| Lockscreen notification defaults | `AssistantReplyNotifications` | Reply content defaults to public and system-generated contextual actions default to enabled. The owner can change `replyLockscreenContentVisible` and `replySystemContextualActionsEnabled` through app settings. Private visibility and a generic public version are used only when the owner switches lockscreen content off. Existing Android notification-channel choices remain authoritative. |
| Clipboard, media and historical event reads | Native phone tools and result visibility | Current Android grants, actual foreground eligibility where required, and explicit owner settings are applied again to stored results. A historical observation does not establish a current OS grant or prove that a previously selected photo is still selected. |
| Original memory, correction and deletion | `MemoryGateway`, `SourcePrivacyLedger`, `SourceRecordVisibility`, `MemoryReviewCoordinator`, backup/restore classes | Original hashes, evidence/author provenance, corrections, exact review scope and durable owner deletion/exclusion are retained. They implement the owner's existing requirement that memory stay accurate and excluded/deleted data not reappear after restore. |
| Steering, pause and uncertain outcomes | `AssistantRuntime`, `ActionReceiptJournal`, `GoalLedger`, Work transport | Current owner input and explicit pause take precedence. Durable receipts prevent replaying a mutation whose result is unknown, and accepted/requested is not labeled completed. These preserve actual command identity and truthful history. |

The audit found no global default-deny switch in Android tool permissions: the normal empty permission object means all known features are permitted. Unsupported tools, unavailable OS grants, payload type/size errors and incomplete source evidence are reported separately. Removing application risk policies does not make an unimplemented Android operation available or permit fabricated execution success.

The five new controls are included in `app.settings.get` and validated atomically in `app.settings.update`. Prepared dispatches include these keys in the settings fingerprint. Their owner-facing controls belong in the Permissions screen; existing Android grants and explicit owner source exclusions remain separate.

Focused verification of the configurable defaults on 2026-10-14: **91 tests, 91 passed, zero failures/errors/skips**, comprising `AssistantRuntimeTest` (54), `AssistantReplyNotificationsTest` (30), `OriginBoundaryTest` (2) and `WorkingDownloadPermissionTest` (5). The final Gradle run completed in 28 seconds. The regression starts a tool root at round 24 and executes 13 actions successfully under default settings, then continues to round 26. Separate cases verify owner-selected caps and atomic settings validation. Notification cases cover public defaults, an owner-selected private preview and contextual action switching. Synthetic HTTP connections cover host/path cookie selection, cross-host redirects, HTTP destinations, unsupported URI redirects, partial responses and HTML login responses without contacting a real account or website.

The application manifest now permits cleartext traffic for the requested ordinary HTTP capability. This does not bypass target-site authentication, Android cookie matching, or file completion checks. Lock-screen content remains subject to the phone's global notification and channel settings; an existing user-selected system channel is not silently re-enabled or overridden.
