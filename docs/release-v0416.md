# 호영 0.4.16 — 연결 후 전송이 중단되던 대화 생성 기록 복구

사용자 진단은 설치 버전 0.4.15, 로그인·Work·Medium·Fast 확인 성공, `ready=true`, `lastCode=conversation_journal_unavailable`, 접수된 요청 0건이었다. 따라서 이번 수정은 답변 DOM 인식보다 앞 단계인 네이티브 전송 예약과 대화 소유 기록을 대상으로 한다.

## 변경

- 사용자가 이미 결과를 확인하거나 제외한 요청도 브라우저의 `pendingRequestId`에 남으면, 새 요청의 대화 생성 예약이 충돌했다. 이제 연결 준비 전에 실제 네이티브 요청 상태와 대조한다. 완료·제외된 요청 또는 네이티브의 명시적인 미전송 증거가 있는 예약만 정리한다.
- 정리 이력은 요청별로 영구 보관하고 원문·기억을 유지한다. 이전 작업을 다시 실행하지 않으며, 주소를 잃어 삭제를 확인하지 못한 웹 대화를 삭제됐다고 기록하지 않는다. 실제로 소유한 대화 주소가 있는 경우의 기존 삭제 절차는 유지한다.
- 결과가 불명확하거나 네이티브 요청 자체가 없는 예약은 그대로 보존한다. 이때 웹 모델 선택이 맞더라도 앱이 `연결됨`으로 잘못 표시하지 않는다.
- 장부 저장 실패가 명시적인 미전송 증거를 삼키지 않도록 했다. 저장 오류가 남으면 전송 가능 상태를 표시하지 않고, 재연결 시 저장 가능 여부를 확인한다.
- 전송 전 중단은 해당 요청과 연결된 안내로 대화창에 남긴다. 설정의 `blocked` 표시와 `선택 확인 후 다시 대기` 버튼을 `처리 중단`, `이 요청 다시 시도`로 바꾸고 이유를 표시한다.
- 진단에는 대화 생성 예약, 연결된 네이티브 요청의 상태, 저장 오류를 추가한다. 대화·비밀번호·알림 본문은 넣지 않는다.

기존에 중단된 요청들을 한꺼번에 자동 재전송하지 않는다. 연결 준비가 끝나면 사용자가 원하는 중단 요청만 설정에서 한 번 다시 시도할 수 있다. 아직 `queued`인 새 메시지는 정상 대기열대로 처리한다.

## 검증

- 수정 전: 이전 요청을 확인한 경우·제외한 경우·아직 확인하지 않은 경우의 네이티브 재현 3개가 실패했다. 수정 후 관련 JVM 검사 99개가 통과했다. 전송 전 안내 검사는 사용자 원문과 혼동하지 않도록 시스템 메시지의 역할·요청 ID까지 확인한다.
- 기존 Work 동작: Android 35 독립 가상 기기 5환경에서 13개씩 65개 통과. [실행 기록](https://github.com/dog898996/be3hyu/actions/runs/38736732123).
- 위 실행에 새로 추가한 앱 전체 왕복 검사 1개씩은 재현 코드가 새 페이지 로딩 전에 이전 화면의 준비 상태를 읽어 실패했다. 단순 준비 상태 대신 이번 예약의 정리 영수증까지 기다리도록 검사 코드를 수정했다.
- 최종 앱 전체 왕복 검사: 같은 최종 소스로 5환경 모두 통과(5/5, 첫 실행 4환경 + 태블릿 재실행 1환경). production Runtime → Controller → 대화 장부 → 실제 Android WebView → 네이티브 최종 전송 승인 → 답변 → 앱 대화 저장을 사용한다. 공급자 화면만 오프라인 fixture다. [실행 기록](https://github.com/dog898996/be3hyu/actions/runs/38737665972).
- 태블릿은 SDK 실행기 다운로드 압축 파일 손상으로 앱 검사 전에 중단돼 해당 환경만 같은 소스로 다시 실행했다. 다른 4환경의 통과 기록은 첫 실행에서 보존했다.
- 기존 서명, 48개 manifest 권한, 16KiB 패키징을 확인했다. 브라우저 JavaScript를 변경하지 않아 별도 전체 Chromium 검사는 반복하지 않았다.
